1. A2-02 — one account could suppress everyone's outage reports
---------------------------------------------------------------
`reports.filter(t => t > clearedAfter)` meant ANY single clear cancelled EVERY report at a
location. Three people report a broken bathroom, one account taps "it's working now", all three
vanish — and nothing stopped that account doing it again the moment they were re-filed.

The rules cannot fix this. They cannot tell whether someone is present, whether the restroom is
genuinely restored, or whose report is whose. So the authority model is now in the client and it
is deliberately asymmetric:

  YOUR OWN report        one clear from you cancels it. You are withdrawing your own statement,
                         which needs nobody else's agreement.
  SOMEONE ELSE'S report  cancelling it takes as many DISTINCT clearers as there are outstanding
                         reporters. One account cannot overrule three people.

Server-derived consensus is still the better long-term answer, and the audit is right about that.
This is the part that works without one, and it removes the single-account suppression case.

Tested 8/8:
  1 report, no clear                     1 live
  author withdraws their own             0 live
  a stranger clears a lone report        0 live
  3 reports, ONE stranger clears         3 live   <- this is the fix
  3 reports, THREE strangers clear       0 live
  clear predating the report             1 live   (stale clears do not count)
  2 reports, 1 withdrawn + 1 stranger    0 live
  future-dated clear                     ignored

FOUND WHILE FIXING IT: the same logic existed TWICE
  Bathroom Now's filter had its own simpler copy. Fixing only the popup would have left a single
  account still able to suppress reports there. Both now call one resolveOooReports(), so they
  cannot drift apart again. Three dead locals were removed from loadOoo; I listed exactly which
  lines of executable code were deleted before deleting them, because the surrounding block was
  all comment.


2. SEC-08 — admin amenity overrides accepted any 24-character string
---------------------------------------------------------------------
Override values were `boundedStrOrAbsent(..., 24)`. I tightened community VOTES to an enum in the
Audit #2 pass and left overrides, so the admin path was the looser of the two — which is
backwards.

Now an enum: yes, no, unknown, single, multiple, or empty (the panel's clear value).

Checked against what actually writes them before changing anything: the admin panel emits exactly
yes / no / unknown, all three accepted. Now rejected: "YES", "yes " with a trailing space,
"maybe", markup, and any long string. The app compares these literally, so anything outside the
enum silently read as "not set" anyway — it was accepted at the door and then ignored.

22 validators changed, 11 on create and 11 on update.
