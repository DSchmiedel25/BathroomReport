═══ THE RECAP — you were right to ask ═══
You asked whether the weekly recap is even deployed. I had just used it to justify part of the
H-01 fix, so I checked. It is deployed — the pill is in index.html, the function is complete —
but line 3368 was:

    // loadWeeklyRecap();  // disabled — its stat pill is hidden in the redesign

So I was wrong. I said closing `votes` would "silently reduce the recap to counting only your own
activity". It would not have: the recap does not run. The H-01 fix is still right, but on its own
merits — a public collection carrying uid, location and timestamp is the exposure regardless of
who reads it — and I overstated the breakage to justify it.

It is now re-enabled, and TWO bugs had to be fixed first:

1. It cost one query PLUS a document read per entry. That is why it was disabled.
   Both branches now trust the log. One query for the week, regardless of volume:
      20 entries: 21 reads -> 1
      60 entries: 61 reads -> 1

2. The tip branch was already broken by my own RB-02 restructure. It verified a tip by looking
   for its text in tips/{locId}.tips — the LEGACY array. Tips have lived in a per-entry
   subcollection since v2.8.0, so every new tip failed that check. Had I re-enabled it without
   looking, tips would have silently shown zero forever.

Trusting the log means keeping it honest at the point of deletion:
   votes  recomputeBathroomAggregate deletes the activity entry when a vote is deleted (server)
   tips   FlushPanel deletes it when an admin removes a tip (already an admin action)

INDEXES: none needed. Every query here is single-field — ts >= cutoff, locId ==, sourceId ==.
I deliberately avoided a three-filter query on type+locId+text, because Firestore only tells you
a composite index is missing by failing the first time it runs, and that first time would have
been you, mid-moderation.


═══ ALSO IN THIS BATCH ═══

FUNC-02  eligibility counted vote DOCUMENTS while promising ">=10 ratings". A vote document
         exists as soon as someone answers an amenity question, so amenity-only participation
         granted hours-consensus eligibility. Now counts actual ratings, via select('bathroom')
         so it fetches one field per doc and needs no composite index.

FUNC-04  the consensus recompute awaited two Firestore round trips PER SUBMISSION, sequentially,
         re-resolving the same person every time they appeared. Now each distinct uid resolves
         once, in parallel: 50 submissions from 12 people, 100 serial reads -> 24 parallel.

APP-02   the ratings mirror stored four redundant fields in every entry — clientId (identical),
         locId (it IS the key), username (identical), lastUpdated (unread). 36% smaller, and the
         ceiling moves from ~2,668 to ~3,900 rated locations. The bigger win is that this
         document is rewritten WHOLE on every rating.
         Also capped at 2,500: past 1 MiB the write throws, the catch swallows it, and the mirror
         keeps being READ while silently no longer updating — serving a stale map indefinitely.
