THE DATE PROBLEM — fixed at the root, not the symptom
=====================================================================

You spotted the FAQ saying July 21 after the data was updated. There were actually THREE
hand-typed dates, and they had already drifted apart:

    drawer version stamp       2026-07-30
    onboarding panel           July 14, 2026
    FAQ / how it works         July 21, 2026

Patching the two strings would have guaranteed the same bug next release, so instead there is
now ONE value:

    const BUILD_DATE = '2026-07-30';          // app.js, near CONFIRM_THRESHOLD

buildDateLong() turns it into "July 30, 2026" for prose, and stampBuildDate() fills every
element that shows a date — .onboardingUpdated, .hiw-updated, and the drawer stamp (which now
carries data-version="v2.6.4" so the version and date compose from one place).

ON EACH RELEASE: change BUILD_DATE and data-version. Nothing else displays a date.

The markup keeps July 30, 2026 as a no-JS fallback, so all three now agree even before
stampBuildDate runs. Formatter parses the string as parts rather than new Date(), so it can't
shift a day backwards for users west of GMT. Tested against 2026-01-01, 2026-07-30, 2026-12-25.

DRAWER ALIGNMENT — three causes from your screenshot
=====================================================================

A. Passport was CENTRED. styles.css still listed #passportToggle in the old floating
   map-control stack (position:absolute, justify-content:center). shell.css overrides display,
   width and text-align for drawer buttons but never justify-content, so that one declaration
   survived the redesign.

   My dead-CSS pass in v2.6.3 could NOT have caught this: it only removed declarations where
   shell.css sets the same property. This was an orphan with nothing competing against it.
   FIX: #passportToggle removed from that selector list, and its top:90px rule deleted.

B. Gift shop sat 4px left. It is an <a class="d-shop-link">, so `#appDrawer .d-items button`
   never applied — padding 14px 16px against everyone else's 20px, weight 600 against 700,
   display:block instead of flex. FIX: a matching #appDrawer .d-shop-link rule.

C. Nothing lined up vertically, because every icon was inline text. 🎫 ❓ 🛍️ ⚙️ have different
   advance widths, so the label began at a different x on each row — which is why the menu read
   as ragged even where padding matched.

   FIX: a fixed-width icon column.
       #appDrawer .d-ico{ flex:0 0 1.6em; display:inline-flex; justify-content:center; }

   Ten static rows use it, plus the four group toggles. Those needed a data change as well:
   CK_GROUPS stored the emoji inside the label string ('⛽ Gas & convenience') so it could not be
   placed in the slot. Split into { icon, label }; both renderers updated and labels now run
   through escapeHtml. Sized in em so the column tracks font size, not a magic pixel value.

=====================================================================
WHAT THE AUDIT SHOULD HAVE CAUGHT AND DIDN'T
=====================================================================

The alignment problems and the stale dates were all visible in the files I had. They were missed
because my checks only find what I thought to query. Three checks worth running next time:

  - STALE SELECTORS: any rule whose properties contradict the element's current layout context
    (position:absolute on a flex-column child, justify-content on a row that must be
    left-aligned). This is what hid the Passport bug.
  - SIBLING GEOMETRY: rows in one container that disagree on padding, font-weight or display.
    This is what hid the Gift shop bug.
  - DUPLICATED CONSTANTS: the same value typed in more than one file — dates, thresholds,
    colours. Three dates in three places is why they drifted. (bake-confirmed's MIN_YES vs the
    app's CONFIRM_THRESHOLD was the same class of bug, caught earlier.)
