WHAT WAS BROKEN
---------------
Firestore treats '/' as a path separator. doc(db,'votes','node/123_uid') resolves to
votes/node/123_uid — three segments — and doc() throws, because it requires an even count.

6,595 of 28,123 location ids (23.5%) were OSM-derived and contained a slash:

  speedway 3,180   nyPublic 1,405   nycPublic 983   nycDunkin 396   nycStarbucks 266
  bosPublic 120    bosDunkin 103    bosStarbucks 58   + 6 smaller metro chains

A sanitiser already existed and was applied in exactly two of seven places. Missing from:
votes, aggregates and tips in app.js; ALL FOUR collections in flushpanel.html, which had no
sanitising at all; and functions/index.js, which built aggregates/${locId} server-side.

Every call site was wrapped in try/catch returning an empty value, so the failure was silent:

  rating a Speedway            -> write threw, nothing saved, no error shown
  opening any metro popup      -> aggregate read threw, community average never appeared
  tips on those locations      -> invisible and unsavable
  admin override in FlushPanel -> failed
  the aggregate Cloud Function -> failed for the same records


WHAT CHANGED
------------
1. ids renamed in 13 data files: 'node/123' -> 'node__123'. 6,595 records. Zero collisions.

2. THE ORIGINAL IS PRESERVED: meta.srcId holds the raw form on all 6,595.

   There is deliberately no inverse helper. It cannot be written correctly — 39 ids contain two
   slashes (merged records like node/A+node/B) and one contains a genuine double underscore
   (gp/ChIJTzsjNj5744kRK__m7xpIOck), so no single replace rule reconstructs both, and a
   plausible-looking one would corrupt data in exactly the debugging context you'd trust it.
   meta.srcId is exact. Verified: it reproduces the new id for all 6,595 records.

3. fsId() at every Firestore boundary in app.js, flushpanel.html and functions/index.js.
   Not redundant now that the data is clean, because:
     - links shared before this change still carry ?loc=node%2F123
     - reports / outOfOrder / missingReports / activity store locId as a FIELD, with slashes,
       and those writes DID succeed (auto-id addDoc) — read-time normalisation keeps them
       resolvable, which is why NO Firestore migration is needed
     - a future import can reintroduce slashed ids
   Verified: all three implementations agree on 8 inputs including null, undefined and a number,
   and the function is idempotent, so applying it to an already-safe id is a no-op.

4. RB-04 — live amenity confirmation has NEVER worked, and now does.
   fetchCommunityDoc reads aggregates/{locId}.amen. The Cloud Function returned early on any
   amenity-only change and never wrote `amen`, so amenityCache was permanently all-zeros. The
   accessibility badge, restroom-setup answers and the hasRestroom hide were all inert. The only
   other route was the nightly export-votes -> bake-confirmed bake, which was crashing until
   yesterday. So the feature had never reached a user by either path.

   The trigger now tallies amenity and store-feature answers via nested dot-path increments, and
   stamps schemaVersion: 2. Amenity keys are NOT enumerated in the function — whatever keys
   appear in a vote get tallied, so adding an amenity in app.js needs no redeploy.
   Unit-tested, 8/8: first vote, yes->no change, vote deleted, unchanged, non-yes/no value
   ignored, store features, the new hasRestroom key, and a rating-only change.

   KNOWN LIMIT: `amen` counts votes from this deploy forward. Answers cast before it existed were
   never tallied and are not backfilled. Aggregates are derived from `votes`, so a one-off
   recompute can correct them if the numbers ever look wrong.

5. RB-05 — signing up no longer double-counts. The migration copied each anonymous vote to the
   new uid and deliberately left the original, so the trigger counted both and one rating became
   two in the public average, permanently. Now it deletes the original after a CONFIRMED copy,
   per-document, so a failure can never destroy a rating it did not move. A denied delete is
   logged loudly rather than swallowed.

   WORTH KNOWING: this loop finds nothing today. The votes rule requires signedIn() via
   ownedByCaller() AND pins the doc id to request.auth.uid, so a vote keyed to a device id could
   never have been created — the audit inferred the bug from the code without checking whether
   the source documents can exist. The fix is in so that if anonymous rating is ever enabled, the
   migration is correct from day one.

6. ADMIN-02 and two related bugs. Three travel-chain constants existed with three different
   contents:
     TRAVEL_CENTER_CHAINS  pilotFlyingJ, loves, bucees            <- achievement; OMITTED TA
     TRAVEL_KEYS           'pilot', loves, travelCenters, bucees  <- dead; 'pilot' isn't a key
     TRAVEL_CENTER_KEYS    all four                               <- correct
   So rating a TravelCenters location never counted toward Truck Stop Hero. Now one definition,
   shared. The dead constant is gone.

   FlushPanel derived chain keys by stripping 'Locations' off the global name, giving 'pilot'
   where the registry says 'pilotFlyingJ' — a new store added through the panel was written with
   a chain the app doesn't know, so it never rendered. Now a table, with audit-ui.js failing the
   build if the registry gains another mismatch.
